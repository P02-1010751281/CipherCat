# 上下文基线：反复出现的问题与验收要求

以下内容从此前对话和项目变更中归并为稳定验收要求，不把对话原句当作项目规范。

## 架构与可信测评

- 样本生成和可信测评必须在后端执行；前端是用户构建、生成和试验代码的界面，不是可信测评器。
- 后端执行用户代码必须位于隔离 sandbox/container 中，不允许在普通服务进程里直接执行不可信 `exec(user_code)`。
- 不得伪造报告、401 页面或未登录页面截图；401 是授权边界，不是测评结果。
- 后端应记录样本、参数、代码/项目绑定、规则版本、检测器版本和失败阶段；“参数相同”不能冒充“样本可复现”。
- 隔离环境需要最小权限；共享卷、`777`、跨任务读写和 worker/sandbox 结果篡改都必须单独核验。

## 密码学范围与标准

- ZUC 是序列密码/流密码；不能与分组密码混称。
- ML-KEM、ML-DSA 属于格基后量子密码；SLH-DSA 属于哈希基；McEliece/Goppa 属于码基。
- 采样、多项式、有限域、矩阵、NTT、编码、压缩、哈希/XOF 等是公共构件或原语，不自动等同于完整密码体制。
- 标准 source 层用于保留原文参照；结构化层用于按函数、原语、公式、伪代码、输入输出和算法阶段给 Blockly/用户使用。
- 公式、伪代码和表格需要完整规范单元；短摘录或项目自写摘要必须明确标为摘要，不能伪装成标准原文。
- source 链接、PDF 页码、章节/行号和缺口必须诚实记录；不得为了补齐统计而制造来源链接。

## 文档与 i18n

- 用户文档与开发文档要在文档中心分开，教程采用说明文体，不混入问答、聊天记录或计划草稿。
- 大小写和算法规范名统一；标准名、语言名、Blockly 块名保留 canonical casing。
- 英文文档应区分真正英文内容与明确标注的 source-language fallback。
- 教程每一步使用真实页面截图时，应能说明路由、构建版本、捕获日期、浏览器/分辨率和页面状态；不要求伪造后端报告截图。
- 代码块应使用正确语言标记并高亮，ASCII art 只在确有必要时使用。

## 测试、容器与交付

- Demo/template 回归要逐项运行，但通过登记的 Demo 不等于所有算法参数、负例、拒绝路径或安全认证均已验证。
- `verify:all` 的范围要与 CI、unit、lint、type-check、build、bundle 和 audit 区分。
- Podman/Docker 文档必须与脚本真实支持范围一致；compose GPU profile、CPU 默认栈、`.env` 必填变量和存储驱动问题要实际验证。
- 避免 DSL/AST、过度抽象、复杂重构；优先最小可验证修复（ponytail）。
