## 根因与修复

全量测试导入控制器时，APScheduler 的 `ProcessPoolExecutor` 创建 POSIX semaphore，Python 因此启动 `multiprocessing.resource_tracker`。工作目录清理失败测试原先在 pytest 主进程直接调用 sandbox `_process()`，并把 `RUNNER_UID` 设为当前 UID。`_reap_runner_children()` 按直接子进程和 runner UID 找进程，于是将 pytest 的 tracker 误当成 runner 子进程并发送 `SIGKILL`。之后 semaphore 清理 finalizer 向重启后的 tracker 注销旧资源，触发 `/mp-*` `KeyError`。

进程跟踪捕获到目标进程命令行 `python -c from multiprocessing.resource_tracker import main;main(...)`，并确认 SIGKILL 来自测试 PID。修复只调整清理失败用例的隔离方式：在独立 helper 进程中真实运行 `_process()`、真实执行子进程回收，并在 `finally` 中清理测试临时工作目录；没有 mock 或削弱回收器，也没有改动生产 sandbox 代码。当前容器配置将 supervisor（UID 1001）与 runner（UID 1002）分开。

一名独立 Luna reviewer 复核根因与补丁，确认测试意图保留、临时目录有超时和清理兜底、隔离范围必要且不过度。

全量测试同时暴露了 8 处 `Field(example=...)` 弃用用法。将其改为 `Field(json_schema_extra={"example": ...})`，未改字段默认值或业务逻辑；逐项验证 `LoginBody`、`RegisterBody` 和 `ProjectSaveBody` 的 JSON Schema example 与修改前一致，仓库对应模块不再有该弃用写法。

## 测评任务状态与临时目录

- **MC-02 状态回退：** 当前 controller 在入库时写 `pending`，持久 outbox 仅派发 `pending` 任务，worker 通过带状态条件的原子认领更新到 `running`；controller 派发后没有回写 `running`。新增的快速 worker 时序单测让 enqueue 同步将状态置为 `success`，断言 controller 返回后仍为终态。独立 Luna 复核确认原状态回退路径不存在。该测试执行真实 controller 函数但使用内存回调模拟 worker 完成，不是 DB/Celery 端到端集成测试。
- **MC-03 临时目录：** 检查发现 `_stage_detect()` 创建并写入 `rdd_celery_*` 后，`running_rddetector` 状态更新若异常，会在目录路径交给主任务之前退出；主任务的 `finally` 因此无法清理。现对这一步异常先清理，再裸 `raise` 交由统一失败处理。新增回归通过 Celery task `.run()` 真实覆盖该分支，断言失败码/阶段/原始错误消息和目录已删除。独立 Luna 复核通过。
- 其他已返回目录的解析、终态写回路径由任务级 `finally` 清理；硬终止/进程崩溃不会运行 Python `finally`，持久化临时卷上的孤儿目录仍是运维清理边界。本次没有为其增加恢复层。

## Compare、hash 与复现字段边界

两名独立 Luna reviewer 分别核对实现与文档，未发现 SHA-256 被用于判定统计结果、报告真实性、样本来源或认证。当前三种指纹范围彼此分离：`input_hash` 只覆盖规范化参数；`projectCodeHash` 覆盖执行源码 UTF-8 字节；`sampleHash` 覆盖按序送检的样本字节及其数量/长度。Compare 的 `resultsMatch` 由对齐的检测项、p/q 值、检测结论和 summary 字段计算，环境与 hash 匹配单独返回；hash 值不参与 `resultsMatch`。这不提供签名、来源证明、执行证明或完整可复现性。
