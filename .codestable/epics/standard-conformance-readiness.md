# 全量密码标准符合性准备

## 起点

CipherCat 是 Blockly 密码算法教学与研究前端，包含标准算法、原语、数学辅助块、procedure 模板和可运行 Demo。仓库已有标准覆盖矩阵、官方/研究文献摘录和双语言 Demo 回归，但当前回归明确不等于完整标准测试套件或认证。

仓库基线（以代码和当前清单为准）：

- `src/blocks/index.ts` 的 `ALL_BLOCK_TYPES` 注册 194 个活动自定义块类型；procedure 模板有 29 项注册，其中 3 项与基础块类型重合、26 项是新增类型；两类身份合计 220 个唯一类型。此外 `COMPAT_BLOCK_TYPES` 另注册 1 个仅用于加载存量工作区的已废弃身份 `ctrl_assign`，不在工具箱、不计入 194/220，但由模板门禁强制登记（`README.md`、`docs/standards/CONFORMANCE-INVENTORY.md`）。
- `demos/tests.json` 登记并执行 59 个 Blockly 工作区（`demos/README.md`）。
- `docs/standards/COVERAGE.md` 当前列出 38 条非 `papers/` 目录映射（含标准、研究与进展追踪条目）；`papers/` 是另一个研究材料目录。全项目信息以矩阵和实际目录为准。
- 目前 `verify:all` 的 Demo 规格混合选定标准向量、固定输入回归和性质断言，不能单独证明全部标准条款或官方认证通过。

## 目标

建立可追溯、可重复的标准符合性证据链，使每个在范围内的 Blockly 块、procedure 模板、Demo 均有明确的规范归属与适用测试；对有正式算法符合性测试的端到端实现，以适用的完整测试集及边界/失败用例验收；对不能单独认证的原语和教学构件，按规范条款、输入输出契约、组合关系和性质测试验证，并明确标注其不可独立认证属性。

不把仓库测试、生成代码或覆盖矩阵表述成官方证书。若目标还包括正式认证，须另确定被认证的产品/密码模块、目标市场、实现与运行环境及有资质的检测/认证机构，并作为独立的产品级路线评估。

## 范围

按 owner 选择的 Option A 执行：

- 覆盖仓库标准矩阵中的全部现行标准及明确引用的配套规范；逐项核对版本、状态、勘误、参数集、规范条文、官方向量/测试系统和适用的测试/认证路径。
- 覆盖全部 194 个唯一自定义块、29 个 procedure 模板注册项（包括与基础块重合的 3 项及 26 个新增类型）、59 个已登记 Demo；核对其 JavaScript/Python 实际语义、输入约束、错误路径和上下游组合。
- 将对象分类为：可直接进行算法符合性测试的实现；作为算法必要前置项的原语；通用/数据/控制构件；教学、研究或非标准组合。分类决定测试强度与可作出的声明，不降低任何适用规范要求。
- 建立最小可维护的映射与门禁：对象 → 规范/条款 → 语言生成器 → 测试向量/性质/边界用例 → 证据来源 → 当前结果/缺口。尽量复用项目已有清单与测试脚本，避免另造重复目录或抽象层。

## 非目标

- 不宣称 Blockly 原子块、procedure 模板或教学 Demo 各自获得官方认证。
- 不把覆盖率、随机统计检测、代码生成成功、单个已知答案或与一个库交叉一致误当作认证。
- 未明确具体产品与目标市场前，不启动正式 NIST CAVP/ACVP、CMVP/FIPS 140-3 或中国商用密码产品认证申报；不联系实验室、不提交软件、不产生费用。
- 不以降低教学可读性为代价将所有块重构成密码库，也不扩大到无标准依据的形式化证明或侧信道认证。
- 不提交或 push。提交策略须在 owner 批准 Epic 时单独明确。

## 验收标准（提案）

1. 194 个唯一块类型、29 个模板注册身份、59 个 Demo 均逐项纳入清单；3 个与基础块重合的模板注册项单独核对其模板注册/配置语义，但不重复计入 220 个唯一类型。每项均有明确分类，指向适用规范/条款或记为无直接规范依据并说明理由。
2. 每个有规范依据的块都映射到规范语义、输入输出契约及至少一项能实际触发并判定该语义的测试证据；证据可以是块级测试，或带可追溯断言的父算法向量/组合测试，不能仅因某 Demo 文件引用了该块就算覆盖。无直接规范依据的通用/教学块也须验证其接口契约及被组合使用时的作用。
3. 每个规范化算法/流程的 JavaScript 与 Python 输出均有来源可追溯的适用向量；对于 NIST ACVP/CAVP 等有参数化测试集者，记录目标算法/模式/参数集以及完整官方测试数据或正式测试系统状态，不能以样例替代完整性。非标准/教学组合采用有来源的性质、边界和错误路径测试，并标注非认证。
4. 共享原语的前置测试关系明确；组合算法不得因端到端样例通过而跳过官方规定的前置算法测试。
5. 所有 Demo 在两种生成语言中可执行；标准向量、固定输入回归和性质测试分层标识，失败可定位到块/算法/规范条款。
6. 明确报告“仓库内符合性证据”与“第三方正式验证/认证”的边界；任何尚未达到的参数集、标准、部署环境或证书状态均有显式缺口记录。
7. 全套相关静态检查、单元测试、所有 Demo 和构建通过；独立审查确认清单、规范来源、向量完整性、测试判定及公开声明没有超范围或无证据结论。

## 共享语言与概念边界

- **标准符合性证据**：可复核的规范条款映射、实现范围、适用测试向量/条件、运行结果及版本信息；不等同于由主管项目签发的验证/认证证书。
  - 不包括：仅仅有一个标准目录、示例 Demo、算法名称或“通过”徽章。
  - 关系 / 不变量：事实权威来自规范发布者和其指定验证计划；每项测试结论限定于被测实现、参数集、版本、语言和执行环境。
  - 来源：NIST CAVP 前置算法要求、FIPS 140-3 CMVP；中国商用密码产品认证目录与实施意见。
- **正式认证/验证**：由适用的官方计划、授权/认可实验室及认证机构按对应对象、范围和流程完成的结果。
  - 不包括：本仓库的回归结果或 CI 状态。
  - 关系 / 不变量：算法验证针对特定算法实现及其参数；模块/产品认证针对定义清晰的产品或密码模块，不会自动赋予其所有 Blockly 块独立证书。
  - 来源：NIST CMVP 与 SAMR/NCA 商用密码检测认证规定。
- **可独立认证构件**：规范或正式计划明确界定了单独受测算法/产品边界的构件。若某个 Blockly 块只是数据转换、整数运算、循环控制、参数装配或标准内部函数，则不能仅因它对应一个函数名而宣称可独立认证；应测试其契约及在被测算法中的规范作用。

## 路线选择依据

- NIST CAVP 说明高层密码功能需分别验证其所依赖的前置算法，ACVTS 对高层功能的测试聚焦该算法本身。
- FIPS 140-3 覆盖密码模块的设计、接口、认证、软件/固件安全、运行环境、物理安全、自检、生命周期等要求；CMVP 由独立认可实验室测试后再进入验证流程。
- 中国商用密码检测认证采用发布的产品认证目录、认证规则和具备资质的检测/认证机构；目录按产品类型及认证依据定义，不是给任意单个密码原语发证。
- 本次调研以 2026-09-29 为核对日期；官方来源见下方链接，执行前仍须更新版本和政策状态。

## 关键决策

- **DEC-1 · 本 Epic 中“过标准认证”的目标含义**：按全量符合性准备推进；所有仓库标准目录纳入核对，所有在范围对象接受其适用的可重复验证；不可独立认证的构件通过规范条款、契约和组合关系覆盖，不宣称已获得正式证书。依据：owner 选择本 Epic 的 Option A（2026-09-29）。

## 子项契约

1. **ITEM-1 · 全量对象与规范适用性清单**
   - Owning skill：`cs-feat`
   - 交付：以现有覆盖矩阵和注册清单为基础，对 194 个唯一自定义块、29 个 procedure 模板注册身份、59 个 Demo 逐项核对身份、生成语言、父算法/规范条款、支持状态和可独立测试性；将 3 个重合模板身份单独关联到基础块但不重复计数，并将无规范依据、未实现或仅研究展示项明确标出。
   - 依赖：无。
   - 验收：每个对象可从清单追到代码/工作区及规范语义、输入输出契约和验证证据；无遗漏、重复身份或把研究内容标成正式标准；194/29/59 的身份计数与 220 个去重类型由自动检查复核。
2. **ITEM-2 · 规范版本与测试证据基线**
   - Owning skill：`cs-feat`
   - 交付：核对全部标准目录的现行版本、适用条款、勘误、参数集及权威测试来源；收集可公开且许可允许的官方向量/测试数据，记录无法离线分发时使用的正式验证系统路径。对已有向量标记来源、版本、覆盖维度和完整性。
   - 依赖：ITEM-1。
   - 验收：每个标准化算法端点都有适用测试来源及参数范围；不能获得的官方数据或项目不支持项是明确缺口，不以示例代替完整套件。
3. **ITEM-3 · 共用基础块与经典算法符合性**
   - Owning skill：发现既有实现偏离按 `cs-issue`；新增测试门禁按 `cs-feat`
   - 交付：按 ITEM-1/2 清单验证和修复数据/位运算/数组/数论等共用基础块及对称、序列、散列、MAC、AEAD、分组模式相关实现；标准未定义独立认证的基础块以契约和被依赖算法条款覆盖。
   - 依赖：ITEM-1、ITEM-2。
   - 验收：适用标准向量、参数边界、错误输入、双语言等价语义通过；测试失败能定位到块类型和规范条款。
4. **ITEM-4 · 公钥、曲线与后量子算法符合性**
   - Owning skill：发现既有实现偏离按 `cs-issue`；新增测试门禁按 `cs-feat`
   - 交付：按清单验证和修复 RSA、ECDH/ECDSA、EdDSA、X25519、SM2/SM9、ML-KEM、ML-DSA、SLH-DSA、码基/哈希基相关实现与所依赖的数学原语；对仅有研究材料、没有标准化实现或测试方案的对象准确降级标识。
   - 依赖：ITEM-1、ITEM-2；共享散列/编码原语复用 ITEM-3 已验收结果。
   - 验收：适用参数集的向量、正反向/往返、拒绝路径及跨语言结果通过；未支持对象不被描述为符合标准。
5. **ITEM-5 · KDF、口令派生与随机生成相关实现**
   - Owning skill：发现既有实现偏离按 `cs-issue`；新增测试门禁按 `cs-feat`
   - 交付：验证 DRBG、GM/T RNG、熵/种子接口、HKDF、PBKDF2、Argon2 等现有块与流程；区分确定性算法向量验证和熵源/随机性统计测评，不把前者当成后者。
   - 依赖：ITEM-1、ITEM-2、ITEM-3。
   - 验收：算法适用向量、生命周期/参数边界及错误路径通过；如需对熵源作可信统计结论，明确引用后端测评证据，不由浏览器回归替代。
6. **ITEM-6 · Procedure 模板和全部 Demo 闭环**
   - Owning skill：正确性缺陷按 `cs-issue`；缺少可重复覆盖按 `cs-feat`
   - 交付：核对并修复所有模板和 59 个 Demo；每个算法 Demo 对准相应标准端点，每个非标准教学 Demo 使用明示的性质/固定输入回归；运行 JavaScript 与 Python 生成结果并验证。修正文档中“官方向量/完整认证”等超出证据的说法。
   - 依赖：ITEM-3、ITEM-4、ITEM-5。
   - 验收：所有工作区可加载、可生成、可执行；已登记断言有权威来源或明确的性质定义；向量、固定输入和教学性质测试标签不混淆。
7. **ITEM-7 · 自动门禁、覆盖文档与发布声明**
   - Owning skill：`cs-feat`
   - 交付：把漏项检查接入现有验证流程；让任一块、模板、Demo 或标准映射新增/删除时能发现失配；更新用户/开发文档及标准覆盖矩阵，准确展示测试层级和残余缺口。
   - 依赖：ITEM-1 至 ITEM-6。
   - 验收：CI/本地门禁覆盖映射与双语言全量回归；说明证据范围、不能推出的结论和外部正式认证边界，不制造“认证通过”徽章。
8. **ITEM-8 · 集成验收与独立最终审查**
   - Owning skill：`cs-epic`
   - 交付：全项目测试、构建和 Demo 集成验证；由 fresh reviewer 按批准标准进行独立验收审查，修复审查问题并复核。
   - 依赖：ITEM-1 至 ITEM-7。
   - 验收：所有批准的验收项通过或有 owner 明确接受的残余；报告附对象覆盖数量、测试数据/参数集范围、未覆盖项和外部证书状态。

## 整体验收

按上方 7 项验收标准整体验收。仅有 Demo 数量、代码生成成功率或少量 KAT 通过，不构成完成；适用测试源、参数范围、生成语言和执行环境均须留证。未取得的正式证书必须如实标为未申请/未验证。

## 遗留风险

- 正式认证资格、实验室评估结论与证书只能由相应外部计划和授权机构决定。
- 标准、ACVP 方案、测试向量和 errata 会更新；清单需记录具体版本与获取日期，不能静态声称永久符合最新版。
