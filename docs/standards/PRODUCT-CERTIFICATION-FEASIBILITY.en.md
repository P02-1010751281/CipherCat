# Product certification feasibility and boundary

> Research baseline: 2026-09-30. This document proposes candidate boundaries and a preparation path; it is not an application, third-party finding, or certification claim.

## Conclusion

CipherCat as a whole—and every Blockly block, Procedure template, and Demo—should not be treated as one certification object. They are different assets in an educational programming platform. Formal validation applies to a defined cryptographic algorithm implementation or a bounded cryptographic module and its specified operational environment.

Keep CipherCat as a teaching, research, and pre-validation platform. If production deployment or a procurement requirement justifies certification, select one independently bounded, versioned cryptographic software module with a fixed interface. Exclude user workspaces, arbitrary block compositions, the generated-code editor, Procedure templates, and Demos from that module boundary. Do not split repositories or scaffold a certification architecture before the target market and product requirement determine the boundary.

The owner has selected a new fixed cryptographic module as the first product candidate and requires it to connect to a randomness source. This selects a product direction and mandatory capability; it does not mean the current code is already a product. The source interface layer, whether the source is inside the module's validation boundary, the target market, and the applicant remain undecided.

## Current product objects

The current inventory lists **194 unique block types, 29 Procedure template identities, and 59 Demo workspaces**. The [conformance-object inventory](./CONFORMANCE-INVENTORY.md) records identities, relationships, and existing evidence. These counts define review scope; they do not mean that each item has been independently tested by a laboratory.

This boundary also matches the repository today: the [architecture guide](../guides/ARCHITECTURE.md) and [`package.json`](../../package.json) describe a Vue/Blockly application. The npm package is marked `private` and has no public module export entry. The [code-generation entry point](../../src/composables/generator.ts) turns a workspace into user-editable JavaScript/Python code rather than publishing a cryptographic module with a fixed interface, version, and operating environment. The Tauri app bundles the same frontend `dist`; its Rust side is currently an application shell with Tauri plugins and serialization dependencies, not a cryptographic module implementation or service API. Thus, cryptographic code inside the generators is an asset of the teaching platform, not an independently delivered cryptographic product. Generated code may rely on browser Web Crypto, the Python standard library, or project implementations. A shared block ID or teaching-algorithm label therefore does not establish one certifiable implementation.

The paired Metacrypto repository also has no fixed cryptographic module that can simply be nominated as this candidate. Its `randomness/` Go module is a statistical-test library; the public `lcplt/` description limits the CUDA component to linear-complexity testing of existing sequences and explicitly says it does not generate samples. The backend's DES code belongs to a brute-force tool, while its SM4 implementation sits in the dynamic MCL/CUDA compilation and performance-benchmark path. Their presence does not make them independently delivered cryptographic-service products with a fixed API. Thus, “build a new fixed module” means defining and shipping a genuinely separate product boundary across the current two-repository state, not relabeling the assessment platform. Read-only evidence checked on 2026-09-30: `metacrypt_server/AGENTS.md`, `randomness/go.mod`, `lcplt/README.md`, `backend/owl_admin/utils/des_bruteforce.py`, and `backend/owl_admin/mcl_cuda_compiler/`.

### Randomness-source interface for the fixed module

The module must connect to a randomness source through a fixed, testable interface. Start with one explicit contract; a generic provider-plugin framework is not a prerequisite. The interface boundary still needs an owner decision:

- **Consume output from an external RBG:** the module obtains bytes through a fixed interface to a declared external random-bit generator. The source, certificate, construction, operating environment, and connection must satisfy the selected validation scheme before it can be treated as an approved dependency. APIs such as `getrandom`, `/dev/urandom`, or `os.urandom` may provide bytes operationally, but their names alone do not establish validation status. The interface neither automatically includes the source in the module boundary nor removes the need to document the dependency.
- **Consume raw entropy/noise:** the module must additionally define collection, entropy assessment, conditioning, health tests, and the downstream RBG construction. This expands implementation and evidence responsibilities and may invoke separate entropy-source/RBG validation requirements.

**Provisional first-release recommendation (owner decision pending; not a certification conclusion):** Prefer having the fixed cryptographic module consume output from one external RNG/RBG whose evidence can be checked against the target scheme. Do not make raw-noise collection and an internal RBG construction part of the first release at the same time. This narrows implementation responsibility, but does not waive proof of the source's certificate/construction, exact operating environment, connection, or module boundary. Expand to raw-entropy input/internal RBG only if the target scheme or lab requires it, or if the product itself is to be delivered as a software random-number generator. NIST CMVP publishes separate entropy-source and SP 800-90C RBG validation paths, and module certificate entries identify the validated version and operational environment; the exact external dependency must therefore be checked against the target platform and scheme. [NIST entropy-source and RBG validations](https://csrc.nist.gov/projects/cryptographic-module-validation-program/entropy-validations) · [CMVP validated modules and certificate scope](https://csrc.nist.gov/projects/cryptographic-module-validation-program/validated-modules).

The Chinese module route gives “integration” more specific meaning. GM/T 0028-2024 §7.9.2 permits a module to contain an RNG, an RNG chain, or itself be an RNG; approved security functions and sensitive-security-parameter generation/establishment that need random values must use an approved RNG. If entropy is collected outside the cryptographic boundary, the data stream generated from that entropy is protected as a critical security parameter; the collected minimum entropy for each such parameter must be at least 256 bits and at least the parameter's bit length. GM/T 0039-2024 §6.2 requires the applicant to list RNGs and uses, document that approved operations obtain random values from approved RNGs, and allows the tester to verify that evidence. GM/T 0134-2024 §14.4 addresses RNG-state protection under GM/T 0028 and state definition under GM/T 0103. See the [official full texts and checksums](./randomness-certification-sources/README.en.md). Thus the fixed module must connect to an auditable RNG/RNG chain and provide evidence for that dependency; a byte-returning API alone is not sufficient.

In NIST SP 800-90A Rev.1, “randomness source” can mean an entropy source, NRBG, or DRBG; it is not synonymous with physical noise. For a NIST route, however, the source used for instantiate/reseed must still satisfy the applicable SP 800-90A/90C construction and CMVP requirements. Section 8.6.6 additionally requires DRBG entropy input and the resulting seed to be protected at the security strength of the data they protect. During cryptographic-module validation, DRBG entropy input is a CSP and must be obtained within the module containing that DRBG function or from another cryptographic module over a secure channel. This requirement is specific to a DRBG function that consumes entropy input; it must not be generalized to every external random-byte, signature-randomness, or nonce interface. The local GM/T 0103 structured entry likewise treats entropy sources, entropy assessment, post-processing, and testing separately. [NIST SP 800-90A Rev.1](https://csrc.nist.gov/pubs/sp/800/90/a/r1/final) · [GM/T 0103 entropy and health-test entry](./gmt0103-rng/02-Entropy-and-Health.md). China's GM/T 0105-2021 software-RNG model explicitly discusses operating-system entropy sources and system/hardware RNG output as possible inputs. If the product contains the software-RNG component addressed by that standard, it also involves entropy estimation, startup and continuous health tests, and exclusive source access. This shows OS/RNG integration is contemplated by the design guide; it is not blanket certification acceptance for every OS API or fixed cryptographic module. The concrete source, auditable entropy/health evidence, boundary, and applicability must still be confirmed. [Official GM/T 0105-2021 text and provenance](./randomness-certification-sources/README.en.md). An unavailable source or required health-test failure must follow the frozen security policy and return an error/refuse service; it must not silently fall back to an undeclared source. Engineering acceptance must also use test doubles and fault injection to show that randomness-dependent services go through the declared interface and handle faults according to policy. Fixed test values or replacement sources must not provide a production-callable bypass. This is evidence for interface and failure-path behavior only; it does not establish the real source's entropy quality or validation status. The interface layer and source boundary remain open.

For a NIST route, the current FIPS 140-3 Implementation Guidance §9.3.A further distinguishes DRBG entropy-acquisition evidence: actively requesting entropy through a defined source's `GetEntropy()` interface, passively loading entropy/seed from outside the TOEPP, and having an entropy source inside the TOEPP without direct `GetEntropy()` access have different outcomes. Some passive external-input scenarios may be validated only with a certificate caveat about assurance of generated SSP strength; an in-TOEPP source without direct access is not validatable under the guidance. This applies to DRBG entropy input, not every external random-output API. Output from a separate RBG module must be assessed against that module's certificate, operating environment, and cryptographic boundary. Freeze the actual call path against the current §9.3.A and confirm it with the submission lab; production must not treat arbitrary caller-supplied seed bytes as equivalent to validated RBG output. [FIPS 140-3 IG and revision history](https://csrc.nist.gov/projects/cryptographic-module-validation-program/fips-140-3-ig-announcements) · [Official local PDF and provenance](./randomness-certification-sources/README.en.md).

**Current implementation gap:** the Blockly teaching generators do not share an injectable randomness adapter and do not define the fixed module's product API.

**NIST callback boundary:** An entropy callback is acceptable only if the path remains a direct connection between the module and `GetEntropy()` and no entity or code outside the cryptographic boundary can manipulate the entropy data; callbacks do not waive the direct-interface requirement.

## Formal routes

### NIST: separate algorithm implementation and module validation

- **CAVP/ACVP:** CAVP validates implementations of approved or NIST-recommended algorithms; algorithm validation is a prerequisite for cryptographic module validation. ACVTS Demo is for preparation and familiarization, not formal validation. Prod is used for formal CAVP algorithm validations and is restricted to accredited Cryptographic Security Testing (CST) laboratories and 17ACVT laboratories. [CAVP overview](https://csrc.nist.gov/projects/cryptographic-algorithm-validation-program) · [ACVTS environments and access](https://csrc.nist.gov/projects/cryptographic-algorithm-validation-program/how-to-access-acvts)
- **CMVP / FIPS 140-3:** the object is a defined cryptographic module, not the entire teaching platform or standards library. Requirements include module specification, interfaces, services and roles, software security, operating environment, sensitive security parameter management, self-tests, lifecycle assurance, and attack mitigation. [FIPS 140-3](https://csrc.nist.gov/pubs/fips/140-3/final) · [CMVP standards and governance](https://csrc.nist.gov/projects/cryptographic-module-validation-program/fips-140-3-standards)
- As of this document’s date, NIST lists FIPS 140-3 validations as currently accepted. New FIPS 140-2 submissions for new validation certificates stopped on 2021-09-22. For U.S. and Canadian federal agencies, FIPS 140-2 modules could be used for new systems through 2026-09-21; beginning 2026-09-22 they moved to the Historical list and may continue only for existing systems. Assess new targets against FIPS 140-3 and the CMVP guidance effective when submitted. [Current CMVP status](https://csrc.nist.gov/projects/cryptographic-module-validation-program)
- **Laboratory access:** The NIST NVLAP/CMVP Bulletin LB-163-2026, issued on 2026-03-09, pauses acceptance of new NVLAP CST laboratory accreditation applications. The pause applies to applications received on or after 2025-01-01 and took effect on the bulletin’s publication date. This concerns new laboratory accreditation applications only. The CMVP page still lists FIPS 140-3 module submissions as accepted and does not announce a suspension of submissions by existing accredited labs. For either CAVP/ACVTS Prod or CMVP, verify an existing lab’s exact accreditation scope, intake status, and schedule; an open program does not guarantee current lab capacity. [NVLAP Bulletin LB-163-2026](https://www.nist.gov/nvlap/nvlap-lab-bulletin-lb-163-2026) · [Current CMVP status](https://csrc.nist.gov/projects/cryptographic-module-validation-program) · [CST Laboratory Accreditation Program](https://www.nist.gov/nvlap/cryptographic-and-security-testing-lap)

For the NIST route, first freeze the implementation, supported parameters, build artifact, and operational environment. ACVTS Demo, project KATs, block tests, and interoperability tests are not CAVP/CMVP certifications. Include only algorithms supported by the selected program and scope.

### NIST entropy sources and random bit generators: not certification of a test service

NIST provides a public [Entropy Source Validation Search](https://csrc.nist.gov/projects/cryptographic-module-validation-program/entropy-validations/search). On 2026-09-30, an unfiltered search showed 356 records across 15 pages (25 per page by default). Focused checks found E8 restricted to vendor reuse, with RHEL 8 / Intel Xeon Silver 4216 listed as its operating environment; E30, E127, and E300 are also vendor-reuse-only. E24 JEnt-MemOnly is marked “Open for Reuse,” but its Public Use Document lists only a specific Ubuntu 18.04 / Intel Xeon 6252 configuration and says incorporation into a FIPS 140-3 module submission requires contacting the implementation provider. A certificate listing or “Open for Reuse” label therefore does not establish arbitrary-platform reuse or automatically satisfy module-submission conditions. The fixed module must retain the ability to connect to a randomness source; the actual source must be checked against the target CPU/OS, interface layer, certificate scope, PUD, and integration conditions after those are fixed. No source was selected and no provider was contacted. This is not a general RBG/DRBG source registry; SP 800-90C RBG submissions use the ESV Server with separate construction evidence. See the [randomness certification source index](./randomness-certification-sources/README.en.md) for details.

Keep three layers separate: SP 800-90B addresses entropy sources; SP 800-90C addresses random bit generator (RBG) constructions that combine entropy sources, deterministic random bit generators (DRBGs), and related components; FIPS 140-3/CMVP addresses cryptographic modules providing cryptographic services. The current CMVP Management Manual uses ESV for both entropy-source and RBG-related submission processes, while explicitly noting that there is no separately defined “Entropy Source Validation Program.” Thus, “ESV” does not mean one generic SP 800-90B certificate. The 2026 manual states that a new FIPS 140-3 module submission requiring entropy-source or RBG validation must reference an existing applicable validation certificate; entropy validation is no longer submitted as an ENT item within the module submission. [CMVP ESV processes](https://csrc.nist.gov/projects/cryptographic-module-validation-program/entropy-validations/esv) · [FIPS 140-3 Management Manual §4.8](https://csrc.nist.gov/csrc/media/Projects/cryptographic-module-validation-program/documents/fips%20140-3/FIPS-140-3-CMVP%20Management%20Manual.pdf)

- **Entropy source (SP 800-90B):** the object is a specific noise source and its sampling, entropy estimation, health tests, restart behavior, and identified operating environments. Submission material includes an Entropy Assessment Report, Public Use Document, Data Collection Attestation (depending on collection method), and raw data. A qualified lab submits through the production ESVTS; the Demo environment cannot produce a formal validation. This is not equivalent to passing a handful of statistical tests on output samples. The current FIPS 140-3 Implementation Guidance D.K, Resolution 23 (2026-08-19 edition, printed pp. 207–208), further interprets the operating-condition requirement: a physical noise source must define the range in which it operates correctly and support similar entropy rates across that range. The guidance recommends comparing statistical-test results from data collected under impactful conditions such as temperature, voltage, and system activity, or justifying that the data cover worst-case conditions. Multi-condition evaluation is a strong recommendation through 2026-12-31 and a requirement afterwards; the guidance allows alternative justifications case by case. It applies to physical noise sources in NIST entropy evaluations, not generically to every external RBG/random-byte interface; the applicable guidance and lab determine the sampling plan once the source and environment are known. [NIST entropy validation](https://csrc.nist.gov/projects/cryptographic-module-validation-program/entropy-validations) · [ESV submission documents](https://csrc.nist.gov/projects/cryptographic-module-validation-program/entropy-validations/documents) · [FIPS 140-3 IG revision history](https://csrc.nist.gov/projects/cryptographic-module-validation-program/fips-140-3-ig-announcements)
- **RBG construction (SP 800-90C):** the object is the complete random-bit-generation construction and its entropy-source dependencies. An RBG report is required; a submission may include an entropy source or reference an already validated entropy source or RBG certificate. CMVP began accepting submissions justifying SP 800-90C RBG conformance on 2026-05-07 and published an RBG Report Template v1.2 update on 2026-06-26; this confirms program intake only, not lab availability or product conformance. [NIST ESV announcements](https://csrc.nist.gov/projects/cryptographic-module-validation-program/entropy-validations/announcements-1). These certificates make different claims and are not interchangeable. RBG1, in particular, constrains the lifecycle of its internal DRBG (one instantiation, no reseed, and output limited by the DRBG seedlife). Its external randomness source must meet the specified RBG2(P), RBG3, or RBGC construction requirements and provide instantiation material through a physically secure channel. RBG1 is not a generic external byte-provider API. Any product using this construction must be designed against [final SP 800-90C §4](https://csrc.nist.gov/pubs/sp/800/90/c/final); use must terminate on seedlife exhaustion or required health-test failure, and the exact configuration, source certificate, operating environment, and boundary must be confirmed with the target CST lab. An OS random API alone is not evidence of an approved source.
- **CipherCat’s current randomness assessment:** the backend executes a candidate implementation in an isolated environment, collects its sequences, and produces statistical assessment evidence for that run and implementation. It does not thereby become a noise source, software RNG, or NIST-validated RBG. Passing statistical tests does not establish entropy, unpredictability, or SP 800-90B/90C conformance. A future RNG product would need its own boundary and entropy source, plus real raw-noise data, collection environments, entropy model, health tests, and evidence for the complete construction.

The project keeps the official PDFs for [NIST randomness-source and module-validation references](./randomness-certification-sources/README.en.md), including SP 800-90B, SP 800-90C, FIPS 140-3 Implementation Guidance, and the CMVP Management Manual with checksums. Reconfirm applicability against the versions effective at submission and written lab guidance.

### China: classify the commercial cryptographic product first

Commercial cryptographic product certification follows applicable catalogs, product rules, and appropriately qualified bodies; it is not a source-code endorsement for using a particular algorithm. The first-catalog PDF is the direct evidence for category 22, “other cryptographic modules,” its inclusion of software modules, and the GM/T 0028 basis; the announcement page provides the [publication and rules entry](https://www.nca.gov.cn/sca/xwdt/2020-05/11/content_1060749.shtml). Cite the [catalog PDF](https://www.nca.gov.cn/sca/xwdt/2020-05/11/1060749/files/2dafffd5b75d4e25aab610f357bb5ec9.pdf) for that row. The second catalog lists GM/T 0103, GM/T 0105, and GM/T 0028 for software RNGs, and GM/T 0078, GM/T 0103, and GM/T 0028 for hardware RNGs. A note to the third catalog requires randomness testing for the products listed in that catalog to follow GM/T 0005 and GM/T 0062. The two catalogs have different scopes; the third-catalog note is not a universal basis for every RNG or cryptographic module. [Second catalog](https://www.nca.gov.cn/sca/xwdt/2022-07/14/content_1060931.shtml) · [Third catalog](https://www.nca.gov.cn/sca/xwdt/2025-03/27/content_1061246.shtml)

The national standards information service's [GM/T 0105-2021 record](https://std.samr.gov.cn/hb/search/stdHBDetailed?id=E66CC4F6F8DB8B7FE05397BE0A0A6C55) confirms the title *Software Random Number Generator Design Guide*, current status, and effective date of 2022-05-01; the State Cryptography Administration's [Announcement No. 43](https://www.oscca.gov.cn/sca/xxgk/2021-10/19/content_1060880.shtml) lists the same standard. The national service's industry-standard portal also exposes “online preview/download standard” actions. This project downloaded the complete PDF through that public download endpoint; provenance, digest, and scope notes are in the [randomness-source references index](./randomness-certification-sources/README.en.md). If the proposed module only consumes an external source and does not include the software-RNG component addressed by the guide, applicability of individual clauses still needs confirmation against the product catalog and the relevant body's scope decision.

The third catalog also separately cites GM/T 0002 and GM/T 0004 for algorithm requirements. This repository stores the GB/T 32907-2016 and GB/T 32905-2016 source texts for SM4 and SM3. The national standards information service lists the corresponding GB/T/GM/T entries as related standards, but they remain distinct identifiers and records; that listing does not establish identical text, supersession, or equivalent certification requirements.
