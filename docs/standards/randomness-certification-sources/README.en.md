# Official sources: randomness and cryptographic-module validation

This directory stores standards and guides obtained from NIST and the national official standards portal on 2026-09-30 for checking the [product-certification feasibility review](../PRODUCT-CERTIFICATION-FEASIBILITY.en.md). The files are unmodified. Before submission, recheck the versions in force and obtain the testing laboratory's scope interpretation. These standards and guides do not show that CipherCat or a proposed module has been validated.

## Verified findings

- FIPS 140-3 IG §9.3.A, Additional Comment 10, allows a callback to obtain entropy only when the path remains a direct connection between the module and `GetEntropy()` and no entity or code outside the cryptographic boundary can manipulate the entropy data; using a callback alone does not establish direct access.

- SP 800-90A Rev.1 §8.6.5 requires an approved randomness source when a DRBG is instantiated or reseeded. The source must be an entropy source conforming to SP 800-90B or an RBG conforming to SP 800-90C. Merely calling an operating-system random API does not prove conformance to this definition. Section 8.6.6 further requires DRBG entropy input and the seed to be protected at the security strength of the data they protect. During module validation, entropy input is a CSP and must be obtained inside the module containing that DRBG function or supplied by another cryptographic module over a secure channel. This is specific to DRBG entropy input, not a general requirement for every external random-byte interface.
- The current NIST [FIPS 140-3 Implementation Guidance](https://csrc.nist.gov/csrc/media/Projects/cryptographic-module-validation-program/documents/fips%20140-3/FIPS%20140-3%20IG.pdf) (2026-08-19), §9.3.A, distinguishes entropy-acquisition scenarios for a DRBG used in SSP generation. A module actively requesting entropy through a defined source's `GetEntropy()` interface does not have the same evidence path as a caller passively loading external entropy/seed. Passive receipt of entropy from outside the TOEPP is described as a rare scenario and, where allowed, requires the Security Policy to document the input/entropy assumptions and a certificate caveat such as “No assurance of the minimum strength of generated SSPs”; a known amount below 112 bits cannot be validated. If the source is inside the TOEPP but the module lacks direct access to its `GetEntropy()` interface, the guidance says the module cannot be validated. These rules concern DRBG entropy input, not every random-byte API. Output from a separate RBG service is not interchangeable with raw entropy/seed injection and must be assessed against the applicable RBG/module certificate, operating environment, and boundary. Before a NIST design is frozen, map its actual integration path to the current §9.3.A scenario and certificate caveats, then confirm it with the target lab.
- Final SP 800-90C defines RBG1 as a constrained construction, not a generic external-random-byte provider: it is instantiated once, cannot be reseeded, uses a qualifying RBG2(P)/RBG3/RBGC source through a physically secure channel, and must terminate on seedlife exhaustion or DRBG health-test failure. A continuously supplied product must not be labeled RBG1 without analyzing its construction.
- The 2026-04-09 CMVP Management Manual §4.8 says a new module submission that needs entropy-source or RBG validation must cite an existing entropy-source validation certificate or RBG-construction certificate; entropy is no longer submitted as an ENT item on the module certificate. An RBG Full Submission requires an RBG Report justifying SP 800-90C conformance. Certificate and operating-environment scope must match the proposed dependency.
- The NIST [ESV announcements page](https://csrc.nist.gov/projects/cryptographic-module-validation-program/entropy-validations/announcements-1) says CMVP has accepted submissions justifying SP 800-90C RBG conformance since 2026-05-07; an RBG Report Template v1.2 update was published on 2026-06-26. This confirms program intake only; it does not guarantee laboratory availability or show that a proposed product conforms or has been validated.
- NIST's [Entropy Source Validation Search](https://csrc.nist.gov/projects/cryptographic-module-validation-program/entropy-validations/search) is a public entropy-source lookup with fields for certificate number, vendor, implementation name, description, noise-source classification, reuse status, and validation date; the page shows an update date of 2026-08-21. On 2026-09-30, an unfiltered query returned 356 records across 15 pages (25 per page by default). Focused checks found that E8 [Red Hat Kernel CPU Time Jitter RNG](https://csrc.nist.gov/projects/cryptographic-module-validation-program/entropy-validations/certificate/8) is restricted to vendor reuse and lists RHEL 8 / Intel Xeon Silver 4216; E30, E127, and E300 are also vendor-reuse-only. E24 [JEnt-MemOnly](https://csrc.nist.gov/projects/cryptographic-module-validation-program/entropy-validations/certificate/24) is marked “Open for Reuse,” but its [Public Use Document](https://csrc.nist.gov/CSRC/media/projects/cryptographic-module-validation-program/documents/entropy/E24_PublicUse.pdf) lists a specific Ubuntu 18.04 / Intel Xeon 6252 platform and configuration, and says incorporation into a FIPS 140-3 module submission requires contacting the implementation provider. Thus, “Open for Reuse” alone does not establish arbitrary-platform compatibility or satisfy module-submission conditions. No source has been selected for the proposed module: its target CPU/OS is not yet fixed, and each candidate must be matched against its certificate scope, PUD, and integration conditions. The directory is not a general RBG/DRBG source registry; RBG submissions use ESV Server with separate SP 800-90C construction evidence.
- The State Cryptography Administration's current public [commercial-cryptography testing-body directory](https://www.oscca.gov.cn/app-zxfw/xzspsx/symmjcjiancha.jsp?channel_code=c100248) lists testing organizations, scopes, and expiry dates, including RNG and other-module testing scopes; it is not a product or randomness-source certificate register. This bounded search did not verify a public query for specific RNG product certificates; it does not prove that no such register exists. Check the official certification portal after the route is selected.
- The local FIPS 140-3 Implementation Guidance matches NIST's current listing dated 2026-08-19 (SHA-256 verified). D.K, Resolution 23 (printed pp. 207–208), interprets SP 800-90B §3.2.1: a physical noise source must document the operating-condition range in which it works correctly and support similar entropy rates across that range. The guidance recommends comparing statistical-test results from data collected under impactful conditions such as temperature, voltage, and system activity, or justifying that the data represent worst-case conditions. Multi-condition evaluation is a strong recommendation through 2026-12-31 and a requirement afterwards; the guidance allows alternative justifications on a case-by-case basis. It concerns physical noise sources in NIST entropy evaluations, not every external random-byte interface; the applicable guidance and lab determine the concrete test plan. [FIPS 140-3 IG and revision history](https://csrc.nist.gov/projects/cryptographic-module-validation-program/fips-140-3-ig-announcements)
- The FIPS 140-3 Implementation Guidance requirement that an SP 800-208 HBS key-generation entropy source be inside the module's physical boundary is specific to that scheme; do not generalize it to all software modules or DRBGs.
- GM/T 0028-2024 §7.9.2 expressly permits a module to contain an RNG, an RNG chain, or itself be an RNG. Approved security functions or sensitive-security-parameter generation/establishment that need random values must obtain them from an approved RNG. If entropy is collected outside the cryptographic boundary, the resulting data stream generated from that entropy is protected as a critical security parameter; the collected minimum entropy for each such parameter must be at least 256 bits and at least the parameter's bit length. The security policy must also describe each RNG, its use, and its entropy source.
- GM/T 0039-2024 §6.2 turns those requirements into submission evidence and test procedures: list approved RNGs and uses, document that random values used by approved operations come from approved RNGs, and have the tester verify that evidence. GM/T 0134-2024 §14.4 requires RNG-state protection under GM/T 0028 and says the state information should follow GM/T 0103. Thus, “connect to a randomness source” requires a fixed interface to an auditable RNG/RNG chain and evidence for its source and dependency; responsibility for entropy input and RNG-state protection must be assigned according to the final validation boundary. A byte-returning interface alone does not establish conformance.
- GM/T 0105-2021 §§5.1–5.2 discuss system entropy sources and system/hardware RNGs as possible software-RNG inputs; §§5.4–5.5 address entropy assessment and startup/continuous health tests, while §7.3 requires exclusive source access. This supports system or hardware RNG integration as a design option, but does not establish that any OS API, external RNG, or proposed fixed cryptographic module meets certification requirements. Applicability must be checked against the product boundary, all applicable standards, and the relevant body's interpretation.
- The full texts of GM/T 0028/0039/0134/0105 were obtained from the national official standards portal. Their availability does not mean a body has accepted a particular OS CSPRNG/external RBG boundary; the target product's source, certificates/dependencies, operating environment, and validation scope still require confirmation by appropriately qualified bodies.
